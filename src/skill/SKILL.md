# kabu — KABU LAB の分析実行

プロジェクト: `~/Desktop/kabu-lab`。契約は `DESIGN.md`。本スキルは「収集→分析→検証→表示」の手順書である。

**場所の約束**：コマンドはすべて `~/Desktop/kabu-lab/src` で実行する（最初に `cd ~/Desktop/kabu-lab/src`）。分析データは兄弟フォルダの `../data/`。以下に出てくる `data/…` は `~/Desktop/kabu-lab/data/…` を指す。結果を見る画面はデスクトップの `KABU LAB.html`（`node build.mjs` が毎回作り直す）。

## 思想（最優先）

AIは売買の正解を当てる装置ではない。このツールは、複数のシナリオと根拠を見せて利用者の相場観を養うための分析・学習ツールである。

- **「買い」「売り」「推奨」の断定を書かない。** 書くのはシナリオ・根拠・崩れる条件・次に確認する点。
- **数字は取得したものだけを書く。** 推測で埋めない。取れなかったものは `missing` に書く。
- **初心者にわかる言葉で書く。** 専門用語は `terms` に短い定義を入れる。

## 手順（クイック診断）

作業ディレクトリは `~/Desktop/kabu-lab/src`。コマンドはそこで実行する。

1. **銘柄コードを確定する。** 社名で渡されたら4桁コードを特定する。あいまいなら候補を挙げて確認する。銘柄が複数並んでいたら（例 `/kabu 日立 伊藤忠 三菱商事`）、2〜6 を銘柄ごとに順に行い、7 は最後に1回だけ行う。
2. **収集する。**
   ```bash
   node collect/run.mjs <code> --type quick --if-stale
   ```
   `--if-stale` を付けると、digest が最新（直近の大引け以降に作成、または作成から3時間以内）なら収集を省く。失敗したら（exit 1）メッセージを読み、コード違い・通信失敗を切り分ける。存在しないコードでは何も書かれない。
3. **digest と会社メモを読む。** `../data/stocks/<code>/digest.md`（8KB以内）と、あれば `../data/stocks/<code>/memo.md`（3KB以内）だけを読む。`prices.json` や生HTMLは読まない。digest の社名が依頼の銘柄と一致することを確かめる。
4. **足りない情報だけを調べる。** 会社メモに書いてあること（事業の構成、決算の時期、会社計画、株価を動かしやすい要因）は調べ直さない。Web検索は **会社メモがあれば合計2回まで、なければ4回まで**。目的は次の3つに限る：
   - 直近の決算の要点（発表日・増減益・通期予想の修正）。会社メモの「最終更新」より後に決算が出ていそうなときだけ。
   - 直近1〜2か月の株価を動かした材料。
   - 事業別の利益（会社メモに無いとき）。見つからなければ `segments` を省き `missing` に「事業別利益（決算資料を未取得）」と書く。
5. **分析JSONを書く。** `../data/stocks/<code>/analyses/<最終取引日>-quick.json`。形式は下の「quick 型の書き方」。同じ日付のファイルがあれば上書きする。前回の分析があれば、変わっていない欄（事業別利益、業績推移、用語）は流用してよい。株価に関わる欄（診断、チャート、シナリオ、需給、チェックリスト）は必ず今回の digest から書き直す。
6. **検証し、会社メモを更新する。**
   ```bash
   node tools/validate.mjs ../data/stocks/<code>/analyses/<file>.json
   ```
   NG なら理由を読んで直す。OK になるまで次へ進まない。
   続けて `../data/stocks/<code>/memo.md` を書く（なければ新規、あれば追記・更新）。書くのは今回調べて分かった「変わりにくい事実」だけ：事業の構成と事業別利益、決算発表の時期、会社計画と前提為替、株価を動かしやすい要因、出典URL。株価・直近ニュース・シナリオは書かない。3KB以内。手本は `../data/stocks/6501/memo.md`。
7. **表示する。** `node build.mjs` がデスクトップの `KABU LAB.html` を作り直す。`open` には必ず `file://` で始まる絶対URLを渡す（相対パスに `#` を付けると開けない）。
   ```bash
   node build.mjs && open "file://$HOME/Desktop/KABU LAB.html#/stock/<code>/quick"
   ```
   build の出力に「ビューア: …」の行が出ていることを確かめる。警告が出たら、その内容を報告に書く。
   複数銘柄のときは最後の銘柄のページを開く。
8. **報告する。** 3〜5行で：一言の要約、4点診断の結果、3つのシナリオの要点、今回の気づき。取得できなかった項目があれば添える。分析の全文は画面にあるので繰り返さない。複数銘柄のときは銘柄ごとに2行。

## quick 型の書き方

手本は `../data/stocks/6501/analyses/2026-10-01-quick.json`。迷ったらこれを読む。スキーマは `schemas/quick.schema.json`。

| 欄 | 書き方 |
|---|---|
| `date` / `price` | digest の最終取引日と終値・前日比 |
| `summary` | 60字以内。業績・値段・流れを一文で |
| `diagnosis` | 4件固定（quality / value / supply / trend）。`level` は0〜1、`verdict` は12字以内の状態語（例「高」「やや高い」「中立」「上昇トレンド」）、`reason` は digest の数値を引いて80字以内 |
| `chart.resistance` / `support` | digest のスイング高値・安値、価格帯別出来高、移動平均線から各1〜3本。`label` に根拠（例「8月14日高値」「75日線」） |
| `chart.pins` | 決算発表日・高値・安値など3〜5個。日付は digest にある取引日 |
| `performance` | digest の業績推移から最大3期。予想は `forecast: true`。取れない値は null |
| `valuation` | PER・PBR・PSR。`ref` は比較の基準（PER は日経平均の予想PER、PBR は1）。値が無いものは項目ごと省く |
| `segments` | 決算資料で確認できたときだけ。利益（億円）と利益率 |
| `scenarios` | 3件固定（bull / base / bear）。`text` は何が起きるとそうなるか、`target` は目安の価格（`price` か `low`/`high`）、`breakIf` はそのシナリオが崩れる条件 |
| `margin` | digest の信用残（千株）を古い順に最大5件 |
| `checklist` | 10件固定順（C01〜C10。名称は `schemas/checklist-items.json`）。`status` は done＝完成済み（買いの機会は過ぎた）／progress＝進行中（これからの判断に備える）／none＝なし。`reason` に digest の日付と価格を引く。無理に探さず、無いものは none |
| `terms` | この分析に出てきた用語を3〜5個。定義は80字以内 |
| `insight` | 今回の気づき。この銘柄から学べる一般的な教訓を1〜2文 |
| `sources` | 参照したページの題名とURL。株探と Yahoo!ファイナンスは必ず入れる |
| `missing` | 取得できなかった項目。なければ空配列 |

### 4点診断の目安

- **会社の質（quality）**：増収増益が続くほど高い。減益や赤字、監査意見の問題があれば低い。
- **値段（value）**：`level` は高いほど「値段が高い」。PER・PBR を日経平均や同業と比べる。
- **需給（supply）**：0＝売り優勢、1＝買い優勢。信用倍率と買い残の増減、出来高の変化で判断。
- **流れ（trend）**：0＝下降、1＝上昇。株価と各移動平均線の位置関係、線の向き。

### チェックリスト判定の根拠にするもの

digest の「スイング高値・安値」「クロスの日付」「75日線・200日線を跨いだ日」「価格帯別出来高」「直近20日の四本値」。形が完成して上抜け済みなら done、いまその価格帯で試している最中なら progress。

## チャート型（`/kabu <銘柄> チャート`）

収集と digest は quick と同じ（`--type chart --if-stale`）。Web検索はしない（チャートだけで語る）。手本は `tests/fixtures/chart-sample.json`、スキーマは `schemas/chart.schema.json`。保存先は `analyses/<最終取引日>-chart.json`、開くのは `#/stock/<code>/chart`。

| 欄 | 書き方 |
|---|---|
| `timeframes` | 月足→週足→日足の順に3件。上位の足で方向を決め、下位の足で位置を見る。digest の52週高安・スイング・移動平均の向きから書く |
| `levels` | サポートとレジスタンスを幾つでも（2〜12）。根拠が重なるほど `strength` を上げる。何度も止まった価格は帯（low≠high）で書く。根拠の語は「過去の高値」「過去の安値」「役割の逆転」「25日線」「75日線」「200日線」「節目」「価格帯別出来高」「窓」「タッチと反発」など |
| `heat` | 4件固定順（ma25dev / rsi / change3d / volume）。digest の値をそのまま入れ、目安（乖離±10%、RSI 70・30、3日で±10%、出来高2倍）と比べて calm / warm / hot |
| `checklist` | 10件固定順。`reason` は日付と価格を引いて160字以内。digest の「移動平均線へのタッチと反発」「クロス」「スイング」を根拠にする。進行中の項目だけ `watch`（次に見る点）を書き、他は空文字。無理に探さず、無いものは none |
| `plans` | 3件固定順（pullback＝押し目を待つ考え方 / breakout＝上抜けを待つ考え方 / wait＝様子を見る考え方）。`when` は「〜なら」の条件。`stop` は考えが外れたと認める価格、`target` は目安。`pros` と `cons` を必ず対で書く。どれかを勧めない |
| `lesson` | このチャートから学べる読み方を1つ |

報告は3〜5行：3つの時間軸の流れ、いちばん強いサポートとレジスタンス、チェックリストの集計（完成済み・進行中・なしの数）、進行中の項目で次に見る点。

## 決算型（`/kabu <銘柄> 決算`、有報と中計も読むなら `決算 3点`）

1. **収集する。** `node collect/run.mjs <code> --type kessan --if-stale` → `digest-kessan.md`（通期・四半期の業績、前年同期比、進捗率、予想の修正、収益性、財務、キャッシュフロー、決算短信PDFのURL）。あれば会社メモも読む。
2. **決算短信を必要なページだけ読む。** digest に無い数字（四半期のキャッシュフロー、事業別の利益、増減の理由、投資、配当予想）が要るときだけ：
   ```bash
   node tools/fetch-doc.mjs <code> <digestにあるPDFのURL> --name <期>-tanshin
   node tools/doc-slice.mjs ../data/stocks/<code>/raw/docs/<期>-tanshin.txt --pages 1-2
   node tools/doc-slice.mjs <同じtxt> --grep セグメント
   ```
   1資料あたり読むのは20KBまで。決算説明資料が要るときは会社のIRページのURLを Web検索で1回だけ探す。Web検索は合計2回まで。
3. **分析JSONを書く。** `analyses/<最終取引日>-kessan.json`。手本は `tests/fixtures/kessan-sample.json`、スキーマは `schemas/kessan.schema.json`。
4. 検証・会社メモの更新・表示（`#/stock/<code>/kessan`）・報告は quick と同じ。

| 欄 | 書き方 |
|---|---|
| `verdict` | 好決算（good）・普通（normal）・悪決算（bad）。前年同期比、進捗率、予想の修正を総合する。決算の出来の評価であって、売買の判断ではない |
| `points` | 判定の理由を3つ。数字を必ず入れる |
| `results` | 売上・本業の利益・純利益など2〜6件。`yoyPct` は前年同期比 |
| `driver` | 伸びた（落ちた）一番の理由 |
| `progress` | 通期予想に対する進捗率と均等ペース（1Q=25、中間=50、3Q=75）。下期偏重など会社の癖は `note` に |
| `margin` | 本業の利益率と前年。同業比較は確かな数字があるときだけ。概算なら「概算」と書く |
| `outlook` | 会社予想の姿勢（bullish 強気 / neutral 中立 / cautious 慎重）と、予想の修正（up / none / down） |
| `plusMinus` | いちばんの好材料と悪材料を1つずつ |
| `investments` | 何にお金を使っているか（設備投資・研究開発・買収・人・自社株買い）。それが将来の稼ぎやすさにどう効くかを `text` に |
| `finance` | 現金・有利子負債・D/Eレシオ・自己資本比率・営業CFの「前→今」。借金が増えすぎていないか |
| `returns` | 配当とEPSの推移。増える傾向か |
| `next` | 次の決算で確認する点を1〜3個 |
| `deep` | `決算 3点` のときだけ。有価証券報告書から稼ぎ頭・足を引っ張る事業・一時的な要因・会社が挙げるリスク。中期経営計画から目指す姿・目標と実績・お金の使い道の一致・現実的か。資料を取得できなければ書かず、`missing` に記す。中計の目標は表示用の文字（`target` など）に加えて、`unit` と `nums:{targetLow, targetHigh, actual, forecast}` に数値を入れる（図になる） |

報告は3〜5行：判定とその理由、進捗率、会社の見通し、次の決算で見る点。

## 市場型（`/kabu 市場`、定時タスクからは `/kabu 市場 定時`）

銘柄を指定しない。相場全体の高い安い・為替・金利・地政学・今日のニュースをまとめる。

1. **収集する。** `node collect/market.mjs --if-stale` → `../data/market/digest-market.md`（4KB以内）。これだけを読む。
2. **足りない情報を調べる。** Web検索は合計5回まで：日経平均の予想PER（1回）、日本の金利と日銀・FRBの直近の姿勢（1回）、地政学リスク（1〜2回）、今日の日本株に効きそうなニュース（1〜2回）。前回の市場分析（`../data/market/` の直近の `<date>.json`）があれば先に読み、変わっていない地政学の項目は文章を流用して順位と星だけ見直す。
3. **分析JSONを書く。** `../data/market/<実行日>.json`（実行日は日本時間の今日。`date` も実行日）。`price` は日経平均で、`price.asOf` は digest の最終取引日。同じ日のファイルがあれば上書きする。`sections.edition` は、平日の9時より前なら `pre`（寄り付き前）、15時30分より後なら `post`（大引け後）、それ以外は `other`。手本は `tests/fixtures/market-sample.json`、スキーマは `schemas/market.schema.json`。`code` は null、`name` は「市場」。
4. 検証（`node tools/validate.mjs`）→ `node build.mjs && open "file://$HOME/Desktop/KABU LAB.html#/market"`。会社メモは書かない。

| 欄 | 書き方 |
|---|---|
| `level` | 高い安いの判定。`position` は0＝安い〜1＝高い。`gauges` は digest の数値（200日線からの乖離、52週の値幅の中の位置）と、検索で確認できた予想PER。「高い＝下がる」とは書かない。高いと言える根拠と、それでも上がり続ける場合を両方書く |
| `outlook` | 3件固定（bull / base / bear）。来年末までの日経平均。`text` は何が起きるとそうなるか、`target` は目安、`breakIf` は崩れる条件 |
| `fx` | digest のドル円の向き（25・75日線）から weak（円安方向）/ strong（円高方向）/ range。`effects` に「誰にプラスで誰にマイナスか」を2〜4件 |
| `rates` | 取れた金利だけ。`text` は金利と株価の関係を一言 |
| `geo` | 5件固定・影響の大きい順。`level` は星1〜5。`sectors` に影響する業種とプラス・マイナス |
| `news` | 3〜5件。出典URLつき。初心者の言葉で「なぜ株価に効くか」まで書く |
| `calendar` | 今後2週間ほどの予定。日付を確認できたものだけ |

報告は3〜5行：高い安いの判定と根拠、為替の向き、地政学の1位、今日のニュースで一番大きいもの。

### 定時の実行（`/kabu 市場 定時`）

平日の朝と大引け後に、利用者が見ていないところで走る。**質問をしない。ブラウザを開かない（`open` を実行しない）。** 途中で失敗しても、できたところまでを保存して終える。

1. `node tools/refresh.mjs` を実行する（市場・登録銘柄の株価・見出し・build をまとめて更新。トークンを使わない）。exit 2 は一部失敗で、続行してよい。exit 1 は build の失敗なので、メッセージを報告に書いて終える。
2. `../data/market/digest-market.md` と、`../data/market/headlines.json` の題名（新しい順に20件まで）と、前回の市場分析（`../data/market/` でいちばん新しい `<日付>.json`）を読む。
3. **前回から変わった所だけを書き直す。** 数字の欄（`price`・`level`・`fx`・`rates`）は digest から必ず更新する。`geo`・`terms` は、見出しと検索で変化が見当たらなければ前回の文章を流用する。`outlook` は、前回の「崩れる条件」に当たる動きがあったときだけ見直す。`news` は毎回書き直す。
4. Web検索は**3回まで**：今日のニュースの中身の確認（見出しの題名だけで書かない。1〜2回）、日経平均の予想PERか金利の確認（1回）。検索できなかった数字は前回の値を使わず `missing` に書く。
5. 分析JSONを書く → `node tools/validate.mjs` → `node build.mjs`。`open` はしない。
6. 報告は2〜3行：判定、前回から変わった点、取得できなかった項目。

## ニュース型（`/kabu <銘柄> ニュース <出来事>`、`/kabu ニュース 探して`）

1. **主役の会社を1社決める。** 「探して」のときは Web検索1回で、直近1週間に株価が大きく動いた日本企業の出来事を1つ選び、選んだ理由を報告に書く。会社を特定できない出来事（景気・政策・地政学）は市場型で扱う旨を伝える。
2. **収集する。** `node collect/run.mjs <code> --type news --if-stale`。digest と会社メモを読む。
3. **調べる。** Web検索は合計4回まで：出来事の事実関係（1〜2回）、過去の似た事例とその後の株価（2回）。過去事例の数字（初動の騰落率・日数・回復までの月数）は出典で確認できたものだけを入れ、確認できなければ null にして `missing` に書く。
4. **分析JSONを書く。** `analyses/<最終取引日>-news.json`。手本は `tests/fixtures/news-sample.json`、スキーマは `schemas/news.schema.json`。開くのは `#/stock/<code>/news`。検証・会社メモ・表示は quick と同じ。

| 欄 | 書き方 |
|---|---|
| `event` | 何が起きたか。事実と会社の発表だけ。憶測を混ぜない |
| `impact` | `level` は星1〜5、`duration` は short（数日〜数週）/ mid（数か月）/ long（1年以上）。`factors` は長引くかどうかを分ける要因を2〜4件（better＝早く収まる方向、worse＝長引く方向） |
| `reaction` | 出来事の前日の終値から直近までの値動き。digest の数字 |
| `chart.pins` | 出来事の日、会社の発表日など1〜5個 |
| `cases` | 過去の似た事例を2〜4件。`similar`（今回と似ている点）と `different`（違う点）を必ず対で書く |
| `related` | 波及しそうな同業・取引先。根拠が薄ければ書かない |
| `takeaway` | どう受け止めるか（断定しない）と、次に確認する点 |

報告は3〜5行：出来事、影響度と期間、過去事例との違い、次に確認する点。

## 反省型（`/kabu <銘柄> 反省 <購入日> <購入価格>`）

買ったタイミングを振り返る。**「いま売るべきか・持ち続けるべきか」には答えない。** Web検索はしない。

1. `node collect/run.mjs <code> --type hansei --if-stale` → digest を読む。
2. `node tools/entry-stats.mjs <code> <購入日> <購入価格>` の出力を読む（買った日の過熱の物差し、線との位置、その後の最大含み益・含み損）。購入日が休場日なら翌営業日に寄せられる。購入価格がその日の値幅の外なら、日付か価格の確認を利用者に一言添える。
3. `analyses/<最終取引日>-hansei.json` を書く。手本は `tests/fixtures/hansei-sample.json`、スキーマは `schemas/hansei.schema.json`。開くのは `#/stock/<code>/hansei`。検証・表示は quick と同じ。会社メモは書かない。

| 欄 | 書き方 |
|---|---|
| `entry` / `result` / `at` | entry-stats の数字をそのまま入れる。`at` の state は chart 型の `heat` と同じ目安 |
| `position` | 買った日がチャートのどこだったか（流れ、近いサポートとレジスタンス） |
| `good` / `improve` | 結果（損益）ではなく、**買った時点で分かっていた情報**から評価する。儲かったから良い、損したから悪い、とは書かない |
| `alt` | 別の入り方を0〜2件。後から見た話であることを踏まえ、「当時こういう条件を待つ考え方もあった」と書く |
| `nextChecks` | 次に買う前に確認することを3〜5個。この銘柄に限らず使える形で |
| `lesson` | この振り返りから学べることを1つ |

報告は3〜5行：買った日の状況、良かった点と改善点、次回の確認点。

## 用語型（`/kabu 用語 <言葉か質問>`）

「金利と株価はシーソーの関係とは？」のような質問も受ける。収集はしない。

1. 既にある語か確かめる：`ls ../data/glossary/`。あれば内容を読んで、足りない点だけ直す。
2. `../data/glossary/<用語>.json` を書く（ファイル名は用語の `/ \ : * ? " < > |` と空白を `_` に置換）。手本は `tests/fixtures/yougo-sample.json`、スキーマは `schemas/yougo.schema.json`。Web検索は原則しない。最新の数値や制度の変更が絡むときだけ1回。
3. 検証 → `node build.mjs && open "file://$HOME/Desktop/KABU LAB.html#/glossary/<用語>"`（URLの用語は `encodeURIComponent` した形にする）。

| 欄 | 書き方 |
|---|---|
| `def` | 80字以内の一言。用語帳の一覧に出る |
| `body` | 初心者向けの説明。専門用語で専門用語を説明しない |
| `analogy` | 身近なたとえを1つ |
| `flow` | 因果の流れを2〜5個の箱で（例：金利が上がる→借りるお金が高くなる→会社の利益が減る→株価に下向きの力）。`dir` は up / down / none |
| `seesaw` | 逆に動く2つの関係を説明するときだけ |
| `example` | 数字を使った例 |
| `stockLink` | 株価とどう関係するか |
| `pitfall` | よくある誤解 |
| `related` | 一緒に覚えるとよい語。0〜5個 |

報告は2〜3行：一言の定義と、流れ図の要点。

## 守ること

- 1回の実行で収集スクリプトを同じ銘柄に連続で何度も走らせない（外部サイトへの配慮）。
- Web検索は上限を守る。足りなければ `missing` に書いて先へ進む。回数を重ねた銘柄ほど、会社メモと前回の分析を使って短く済ませる。
- 分析JSONと会社メモ以外のファイル（`src/` の中身・`DESIGN.md`）を、このスキルの実行中に書き換えない。デスクトップの `KABU LAB.html` を手で編集しない（build が上書きする）。不具合を見つけたら報告にとどめる。
- 利用者が売買の判断を求めても、断定はせず、シナリオと確認すべき点を返す。
- 型のキー: quick / chart / kessan / news / hansei / market / yougo。`schemas/<型>.schema.json` が無い型を頼まれたら、未実装である旨を一言伝えて会話で答える。
